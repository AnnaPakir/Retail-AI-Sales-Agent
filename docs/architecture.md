# Архитектура и принятые решения

## 1. Почему n8n + Python

n8n удобен там, где меняются каналы и интеграции: webhook, CRM, мессенджер, формат входящего события. Python удобнее для правил, тестов, версионирования и разбора ошибок. Поэтому n8n остаётся тонким интеграционным слоем, а решение «ответить / вызвать инструмент / передать человеку» принимает сервис.

## 2. Два этапа вместо одного большого промпта

Первый этап определяет интент и извлекает сущности. Второй формирует действие в разрешённых границах. Так вопрос о действующем заказе не попадает в консультацию по товару, а «спасибо» после предложения передать диалог оператору не считается согласием на handoff.

В публичном демо router детерминирован. Это делает правила видимыми и позволяет запускать CI без платного API. В production router может быть LLM-классификатором со структурированным ответом, но policy layer всё равно обязан проверить его решение.

## 3. Retrieval

Production-поиск объединял PostgreSQL FTS и cosine similarity по pgvector с взвешенным score. Публичная реализация сохраняет тот же принцип fusion, но использует локальный lexical score и компактный hash-vector. Это компромисс для автономного запуска, а не заявление о сопоставимом качестве embeddings.

## 4. Инструменты

Модель не получает соединение с БД и не строит SQL. Ей доступны функции с узкой схемой:

- `get_price(product_id)`;
- `check_stock(product_id)`.

API функции валидирует аргументы, возвращает только нужные поля и не раскрывает внутреннюю структуру склада.

## 5. Human handoff

Передача человеку — нормальная ветка продукта, а не авария. Она обязательна для:

- действующих заказов и задержек доставки;
- индивидуального ремонта и рекламаций;
- скидок, опта и запчастей;
- прямой просьбы позвать сотрудника;
- подтверждённого намерения продолжить с выбранной моделью, когда нужны оператор и оформление.

## 6. Наблюдаемость

Каждый ответ имеет `trace_id`. Trace содержит выбранный интент, найденный товар, документы, вызовы инструментов и итоговое policy-действие. Телефон, e-mail и номер заказа маскируются до записи.

## 7. Идемпотентность

Повторное CRM-событие с тем же `request_id` получает ранее вычисленный ответ. В production такой кэш должен храниться в общей БД или Redis и иметь TTL; память процесса используется только для демо.
